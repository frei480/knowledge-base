Это одна из самых частых проблем, с которой сталкиваются разработчики и системные администраторы при переходе от интерактивного запуска к автоматическому через `systemd`.

Поведение программы может кардинально поменяться, потому что **среда исполнения (execution environment) в `systemd` значительно отличается от интерактивной сессии пользователя в терминале.**

Вот ключевые различия, которые являются основными причинами проблем:

# 1. Переменные Окружения (Environment Variables)

Это самая распространенная причина.

- **В терминале:** Ваша сессия наследует множество переменных окружения из системных (`/etc/profile`), пользовательских (`~/.bashrc`, `~/.profile`, `~/.zshrc` и т.д.) и сессионных файлов. Самая важная из них — `$PATH`, которая говорит оболочке, где искать исполняемые файлы.
- **В `systemd`:** Юнит запускается с очень урезанным, минимальным набором переменных окружения. Переменная `$PATH` обычно содержит только базовые системные пути (например, `/usr/bin:/bin:/usr/sbin:/sbin`), но не пути к локально установленным программам (как в `/usr/local/bin` или `~/.local/bin`).
    

**К чему это приводит:**
- Программа не может найти другие утилиты или библиотеки, которые она ожидает найти в `$PATH`.
- Отсутствуют переменные вроде `$HOME`, `$USER`, `$LANG` или кастомные переменные, необходимые для конфигурации (например, `DATABASE_URL`).

**Решение:**
- **Использовать абсолютные пути** в командах и скриптах (`/usr/local/bin/my_app` вместо `my_app`).
- **Явно задавать переменные окружения** в юнит-файле с помощью директив `Environment=` или `EnvironmentFile=`.

Пример:
```ini
[Service]
# Вариант 1: Указать переменную напрямую
Environment="PATH=/usr/bin:/bin:/home/user/app/venv/bin"
Environment="MY_API_KEY=1234567890"

# Вариант 2: Загрузить переменные из файла
EnvironmentFile=/etc/my-app-environment

ExecStart=/home/user/app/main.py
```

# 2. Рабочий Каталог (Working Directory)

- **В терминале:** Когда вы запускаете команду (`./my_app`), рабочим каталогом является тот, в котором вы находитесь. Программа может успешно находить файлы по относительным путям (например, `config.json` или `./data`).
- **В `systemd`:** По умолчанию рабочий каталог для сервиса — это корневой каталог (`/`), если не указано иное.

К чему это приводит:
Программа, пытающаяся открыть файл по относительному пути (open('config.yaml')), будет искать его в /config.yaml и, естественно, не найдет.

Решение:
Явно указать рабочий каталог с помощью директивы WorkingDirectory=.
Пример:
```
[Service]
WorkingDirectory=/home/user/my-awesome-app
ExecStart=/home/user/my-awesome-app/start.sh
```

# 3. Пользователь И Права Доступа (User and Permissions)
- **В терминале:** Вы запускаете программу от имени своего пользователя, у которого есть права на чтение/запись в домашнем каталоге и других разрешенных местах.
- **В `systemd`:** По умолчанию сервис запускается от имени пользователя `root`, если не указаны директивы `User=` и `Group=`.

**К чему это приводит:**
- **Запуск от `root`:** Программа может получить избыточные права, что небезопасно. Она может создать файлы, владельцем которых будет `root`, и которые потом не сможет прочитать или изменить ваш обычный пользователь.
- **Запуск от специального пользователя (через `User=`):** У этого пользователя может не быть прав на чтение конфигурационных файлов, запись логов или доступ к сетевым сокетам, которые были доступны вам в интерактивной сессии.

Решение:
Всегда явно указывайте пользователя и группу, от имени которых должен работать сервис. Это считается лучшей практикой.

Пример:
```toml
[Service]
User=www-data
Group=www-data
ExecStart=/usr/sbin/nginx
```
# 4. Отсутствие Интерактивной Оболочки И TTY

- **В терминале:** Программа запускается в интерактивной оболочке (`bash`, `zsh` и т.д.), подключенной к псевдотерминалу (TTY). Она может взаимодействовать с пользователем (читать со `stdin`), а ее вывод (`stdout`, `stderr`) сразу виден на экране.
- **В `systemd`:** Сервис запускается в неинтерактивной среде без TTY. Стандартные потоки вывода (`stdout`, `stderr`) перенаправляются в журнал `systemd` (journald).

**К чему это приводит:**
- Программы, которые ожидают интерактивного ввода (например, запроса пароля), "повиснут".
- Программы могут вести себя по-разному в зависимости от того, подключен ли к ним TTY (например, цвета в выводе могут отключаться).
- Команды вроде `~` для обозначения домашнего каталога не будут работать, так как это функция оболочки (shell expansion), а `systemd` по умолчанию запускает процесс напрямую.

**Решение:**
- Демоны и сервисы не должны быть интерактивными. Все параметры должны передаваться через конфигурационные файлы или переменные окружения.
- Если вам нужно использовать возможности оболочки (например, перенаправление вывода `>` или `|`), запускайте команду через оболочку: `ExecStart=/bin/bash -c "my_command --option > /var/log/output.log"`.

# 5. Порядок Запуска И Зависимости
- **В терминале:** Вы запускаете программу вручную, когда система уже полностью загружена, сеть доступна, базы данных запущены и все файловые системы смонтированы.
- **В `systemd`:** Сервис может запуститься на раннем этапе загрузки системы, когда сеть еще недоступна, а нужная база данных или файловая система еще не смонтирована.

К чему это приводит:
Программа падает с ошибкой, потому что не может подключиться к сети, базе данных или прочитать файл с примонтированного диска.
Решение:
Использовать директивы After= и Wants= (или Requires=), чтобы указать зависимости.
Пример:
```toml
[Unit]
Description=My App Service
# Запускаться после того, как сеть будет онлайн
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/bin/my_app
```

# Как Отлаживать?

1. **Проверяйте логи:** Самый первый шаг.
```sh
journalctl -u your-service-name.service -b
```
    - `-u`: указать юнит.
    - `-b`: показать логи с момента последней загрузки (помогает отфильтровать старые записи).
        
2. **Проверяйте статус:**
```bash
systemctl status your-service-name.service
```
Эта команда покажет, активен ли сервис, его PID, а также последние несколько строк лога.
3. **Имитируйте окружение `systemd`:** Вы можете запустить команду с помощью `systemd-run`, чтобы увидеть, как она поведет себя в похожем на сервис окружении.
4. **Выведите переменные окружения:** Временно добавьте команду для отладки в `ExecStartPre`, чтобы посмотреть, с каким окружением запускается сервис.
```
[Service]
ExecStartPre=/usr/bin/env
ExecStart=/path/to/your/program
```
 После этого выполните `systemctl restart your-service.service` и посмотрите логи (`journalctl -u your-service.service`). Вы увидите все переменные окружения.
  
# Краткая Таблица-шпаргалка

| Параметр                  | Интерактивная сессия в терминале     | Запуск из `systemd`                        | Решение в `systemd`                      |
| ------------------------- | ------------------------------------ | ------------------------------------------ | ---------------------------------------- |
| **Переменные окружения**  | Полный набор (из `.bashrc` и др.)    | Минимальный, базовый набор                 | `Environment=`, `EnvironmentFile=`       |
| **`$PATH`**               | Расширенный, включает локальные пути | `/usr/bin:/bin:/usr/sbin:/sbin`            | Указывать абсолютные пути, менять `PATH` |
| **Рабочий каталог**       | Текущий каталог                      | `/` (по умолчанию)                         | `WorkingDirectory=`                      |
| **Пользователь**          | Текущий пользователь                 | `root` (по умолчанию)                      | `User=`, `Group=`                        |
| **Оболочка (Shell)**      | Интерактивная (`bash`, `zsh`)        | Отсутствует (процесс запускается напрямую) | `ExecStart=/bin/sh -c "…"`             |
| **Доступность сети/БД**   | Обычно все уже запущено              | Зависит от порядка загрузки                | `After=`, `Wants=`                       |
| **`stdin/stdout/stderr`** | Подключены к терминалу (TTY)         | Перенаправлены в `journald`                | `StandardOutput=`, `StandardError=`      |
