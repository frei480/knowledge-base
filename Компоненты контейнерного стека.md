Давайте разберём стек технологий, на котором работают современные контейнеры (Docker и не только). От верхнего уровня — демона Docker, до фундамента — системных вызовов и подсистем ядра Linux.
Когда говорят «контейнеры в Linux», за этим стоит не один процесс, а целый стек компонентов. Главные из них — **dockerd**, **containerd**, **containerd-shim** и **runc**. Вот как они связаны и зачем нужны.

---

# Общая Картина (сверху вниз)

```
docker CLI  →  dockerd  →  containerd  →  containerd-shim  →  runc  →  процесс контейнера
```

Каждый уровень добавляет свою абстракцию и снимает часть ответственности с нижнего.

---

### 1. dockerd (Docker Daemon)

`dockerd` — долгоживущий процесс, принимающий команды от CLI (`docker run`, `docker build` и т.п.) через REST API (Unix-сокет).

- **Что делает:**
  - Управляет объектами верхнего уровня: образами, контейнерами, сетями, томами.
  - Скачивает и распаковывает образы.
  - Отдаёт команды на создание контейнера низлежащему слою — **containerd**.
  - Хранит состояние запущенных контейнеров (чтобы после перезапуска демона можно было восстановить управление).

Сейчас docker — это в первую очередь удобная «обёртка» для пользователя и интегратор всех функций вокруг контейнера. сам `dockerd` **не создаёт** контейнеры напрямую через ядро — он делегирует это `containerd`. 

---

### 2. containerd (Container Runtime High-Level)
`containerd` — это демон-менеджер контейнеров, изначально вычлененный из Docker, а теперь независимый проект CNCF (Cloud Native Computing Foundation). Он может работать и без Docker, будучи использованным Kubernetes (через CRI) или напрямую.

- **Задачи:**
  - Управление полным жизненным циклом контейнера: создание, запуск, остановка, удаление.
  - Передача образов (push/pull, хранение слоёв).
  - Управление снапшотами файловых систем (часто через overlayfs).
  - Управление сетью (опционально, через CNI-плагины).
  - Запуск низкоуровневого рантайма **runc** через промежуточный процесс — **shim**.

`containerd` предоставляет gRPC API, которым пользуется `dockerd`, и сам внутри себя использует свою версию runc.

---

### 3. shim (containerd-shim)
Это маленькая программа-посредник, которая становится родительским процессом для контейнера (того, что запускает runc). Зачем она нужна?

- **Проблема без shim:** если `containerd` по какой-то причине перезапускается (обновление, сбой), все процессы контейнеров, будучи дочерними для runc (а тот — для containerd), могут быть убиты или потерять связь с демоном.
- **Решение:** после запуска контейнера `containerd` создаёт процесс `containerd-shim`, который вызывает `runc`. `runc` делает свою работу и завершается, а shim остаётся родителем контейнера (PID 1 которого — инициализатор контейнера). Таким образом, жизненный цикл контейнера не привязан напрямую к containerd.

**Функции shim:**
- Поддержание каналов ввода-вывода (`stdout`/`stderr`) даже после остановки runc.
- Передача кода завершения контейнера обратно в containerd.
- Обеспечение того, что контейнер продолжает работать независимо от демона containerd (daemonless containers).

---

### 4. runc (Low-Level OCI Runtime)
Та самая утилита, которая действительно создаёт и запускает контейнер.
Эталонная реализация стандарта OCI (Open Container Initiative). Это CLI-утилита, которая создаёт и запускает контейнер, напрямую используя возможности ядра Linux. После выполнения своей основной задачи `runc` завершается.

**Что делает runc при запуске контейнера:**
1. Читает OCI-спецификацию (JSON-файл `config.json`), в которой описано: корневая файловая система, монтирования, процесс, который нужно запустить, параметры изоляции.
2. С помощью системных вызовов ядра настраивает окружение:
   - `unshare` + `clone` с флагами `CLONE_NEW*` — создаёт **пространства имён (namespaces)**.
   - Записывает в cgroupfs — настраивает **cgroups**.
   - Монтирует `/proc`, `/sys` и корневую ФС контейнера.
   - Выполняет `pivot_root` (или `chroot` в простейших случаях) для смены корневого каталога контейнера.
   - Запускает целевой процесс (init контейнера) в изолированном окружении.

После того как контейнер запущен, `runc` может использоваться для управления уже работающим контейнером (например, `runc exec` для выполнения команд внутри).

### 5. namespaces (пространства имён)
Главный механизм **изоляции видимости** процессов. Каждое пространство имён ограничивает, что процесс «видит» в определённом аспекте системы. Контейнер — это комбинация нескольких таких пространств.

Основные типы namespaces:
- **PID** – изолирует дерево процессов. Процесс внутри контейнера видит только свои процессы, начиная с PID 1 (который на host-системе может быть, скажем, PID 1724).
- **Mount (mnt)** – изоляция точек монтирования. Контейнер видит свою иерархию ФС, не видит монтирования хоста (если они явно не переданы).
- **Network (net)** – изоляция сетевого стека: свои интерфейсы, таблицы маршрутизации, правила iptables. Именно это позволяет контейнеру иметь собственный IP-адрес и порты.
- **UTS** – изолирует hostname и NIS-имя, можно задать имя хоста внутри контейнера, отличное от хоста.
- **IPC** – изоляция очередей сообщений POSIX, семафоров, разделяемой памяти.
- **User** – изолирует UID/GID. root в контейнере (UID 0) может быть мапленный на непривилегированного пользователя на хосте (очень важно для безопасности).
- **Cgroup** – изолирует представление cgroup-дерева, чтобы процесс внутри контейнера видел только свои ограничения, а не всю иерархию хоста.

Создаются через флаги при системном вызове `clone()` или с помощью вызова `unshare()`.

### 6. cgroups (Control Groups)
Механизм **ограничения, учёта и изоляции ресурсов** для групп процессов.

- **Ограничение (limit):** нельзя отъесть памяти больше заданного лимита, CPU throttling.
- **Приоритезация (weight):** какая группа получит больше cpu-time при конкуренции.
- **Учёт (accounting):** подсчёт потреблённых ресурсов.
- **Изоляция:** например, изоляция использования swap, привязка к NUMA-узлам.

Две версии: cgroups v1 (отдельные иерархии для каждого контроллера) и cgroups v2 (единая унифицированная иерархия). Современные системы (и runc) всё активнее используют v2.

Управление происходит через псевдо-файловую систему `cgroupfs`, обычно смонтированную в `/sys/fs/cgroup`. Когда `runc` создаёт контейнер, он создаёт подкаталог с именем контейнера и записывает туда PID процесса, лимиты и настройки. Ядро автоматически применяет ограничения ко всем процессам в этой группе.

### 7. Системный вызов chroot (и его наследник pivot_root)
Исторически `chroot` был первым простым способом изолировать файловую систему: он изменяет **корневой каталог** для вызывающего процесса и его потомков. После `chroot("/path/to/container/root")` процесс считает, что `/` — это указанный каталог, и не может видеть файлы выше (теоретически).

**Почему chroot недостаточно:**
- Не создаёт новое mount-пространство имён. Процесс может «вырваться» из chroot’а, если у него есть права root и возможность сделать доступ к дескриптору реального корня, либо через `/proc`, либо через `chdir("..")` вне корня.
- Не гарантирует изоляции системной информации из `/proc`, `/sys`.

**pivot_root** — более безопасная альтернатива, используемая в контейнерах:
- Требует нового mount namespace (создаётся через `unshare(CLONE_NEWNS)`).
- `pivot_root(new_root, put_old)` перемещает mount point реального корня в отдельный каталог `put_old`, а новую ФС делает корнем mount-пространства. После этого старый корень можно отмонтировать. Процесс надёжно заперт в новом дереве файловой системы.
- runc использует именно `pivot_root` (если возможно), а не `chroot`.

### Как они взаимодействуют (типичный путь запуска контейнера Docker)
1. `dockerd` получает команду `docker run ubuntu sleep 100`.
2. Он передаёт запрос в `containerd` по gRPC.
3. `containerd` загружает образ, создаёт снапшот файловой системы (snapshotter), подготавливает OCI-спецификацию.
4. `containerd` запускает новый shim-процесс (`containerd-shim`).
5. Shim вызывает `runc create` (который внутри делает `runc init` и настройку изоляции).
6. `runc` делает:
   - `clone` с флагами `CLONE_NEWNS|CLONE_NEWPID|CLONE_NEWNET|...` → новое пространство имён.
   - Настраивает cgroups через запись в `/sys/fs/cgroup/.../container-id/`.
   - Монтирует rootfs, делает `pivot_root`.
   - Запускает указанный в спецификации процесс (sleep 100) с PID 1 в контейнере.
7. `runc` завершается, shim остаётся родителем этого sleep 100.
8. `containerd` получает от shim уведомление, что контейнер запущен, и возвращает результат `dockerd`’у.

При остановке контейнера `dockerd` → `containerd` → shim → посылает SIGTERM процессу контейнера или дожидается его завершения. Ядро, в свою очередь, освобождает cgroups и уничтожает пространства имён после завершения последнего процесса в них.

Таким образом, иерархия такова:  
**dockerd** (верхнеуровневый оркестратор Docker) → **containerd** (жизненный цикл контейнеров) → **containerd-shim** (процесс-надзиратель) → **runc** (низкоуровневый OCI-рантайм, подготавливающий изоляцию ядром) → **Linux Kernel features** (namespaces, cgroups, pivot_root/chroot).

# Что Можно Менять Местами

- **dockerd** не обязателен. Kubernetes общается с containerd напрямую через CRI-плагин, без Docker.
- **runc** можно заменить на более быстрый `crun` (на C), на `kata-runtime` (лёгкая виртуализация) или `gVisor` (песочница на уровне ядра пользователя).
- **containerd-shim** тоже может быть заменён — например, `containerd-shim-kata-v2` для Kata Containers.

Эта модульность позволяет комбинировать компоненты под разные требования безопасности и производительности, не трогая верхний уровень.
