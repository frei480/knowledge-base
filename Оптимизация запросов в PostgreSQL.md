Статья описывает практические, неочевидные приёмы оптимизации сложных SQL-запросов в PostgreSQL, особенно в управляемых средах (managed cloud databases), где нет полного контроля над сервером. Автор делится техниками, которые помогли добиться **10-100-кратного ускорения** запросов с большим количеством `JOIN`-ов и строк.

---
# **Ключевые Техники И выводы**

- **`LEFT JOIN` вместо `INNER JOIN`:** Помогает планировщику точнее оценивать количество строк, предотвращая выбор неэффективного `Nested Loop`.
- **= ANY(VALUES …) вместо `IN`:** Может изменить план запроса на более эффективный `Hash Join`, особенно при большом количестве значений.
- **Расширенная статистика:** Информирует планировщик о корреляции между столбцами, что кардинально улучшает оценку количества строк и выбор планов.
- **Тип первичного ключа:** Использование `integer` вместо `varchar` для первичных ключей значительно ускоряет `JOIN`-ы (в примере автора — в **2-5 раз**).
- **`CLUSTER`:** Физически переупорядочивает строки в таблице согласно индексу, что экономит IOPS при чтении большого количества связанных строк.
- **`pg_hint_plan`:** Мощный инструмент для "подсказок" планировщику, когда его автоматические решения неоптимальны.
- **Инструменты:** `explain.tensor.ru` для визуализации и анализа планов, `Cloud SQL Insights` для мониторинга и выявления проблемных запросов.

# **Подробный Разбор техник**

## Тайное Преимущество `LEFT JOIN`
- **Проблема:** При `INNER JOIN` по коррелирующим столбцам планировщик PostgreSQL может перемножать их селективности и сильно занижать оценку количества строк. Это приводит к выбору неэффективного `Nested Loop Join` вместо `Hash Join`.
- **Решение:** Заменить `INNER JOIN` на `LEFT JOIN`. Планировщик будет ожидать количество строк, равное количеству строк в "левой" таблице, что ближе к реальности.
- **Улучшение:** Добавить избыточное условие в `LEFT JOIN`, чтобы помочь PostgreSQL заранее отфильтровать данные для хэширования.

```sql
    -- Было (неэффективно)
    FROM pull_requests pr
    INNER JOIN commits c ON pr.merge_commit_id = c.id
    
    -- Стало (эффективнее)
    FROM pull_requests pr
    LEFT JOIN commits c ON pr.merge_commit_id = c.id
                        AND pr.repository_id = c.repository_id -- Избыточное условие
```

- **Результат:** Ускорение в **10-100 раз**, особенно в "многоэтажных" `JOIN`-ах.
    

## Хеширование `VALUES` Вместо `IN`

- **Проблема:** Стандартный `WHERE repository_id IN (…)` обычно планируется как `Index` или `Bitmap Scan`.
- **Решение:** Переписать запрос с использованием `ANY(VALUES …)` или `ANY(SELECT * FROM unnest(…))`.

```SQL
    -- Вместо IN (...)
    WHERE repository_id = ANY(VALUES (101), (102), ...);
    
    -- При передаче через параметры
    WHERE repository_id = ANY(SELECT * FROM unnest($1::bigint[]));```

- **Эффект:** PostgreSQL может построить другой план с `HashAggregate` и `Hash Join`, что в некоторых случаях (особенно с другими `JOIN`-ами) работает быстрее.
    
## Расширенная статистика

- **Проблема:** Когда фильтрация идет по нескольким столбцам, которые логически связаны (например, `repository_id` и `merge_commit_id`), PostgreSQL считает их независимыми и занижает оценку количества строк. Это ведет к неверному выбору планов.
- **Решение:** Создать объект статистики, который сообщит планировщику о корреляции.

```SQL
    CREATE STATISTICS ids_correlation
    ON repository_id, merge_commit_id FROM pull_requests;
```

- **Результат:** Планировщик корректирует оценку строк, выбирает `Hash Join` вместо `Nested Loop` и ускоряет запрос в **10-100 раз**. Особенно полезно при шардинге.

## Тип Первичного Ключа

- **Проблема:** Использование `varchar` (строк) в качестве первичных ключей, особенно из внешних систем, замедляет `JOIN`-ы. Строки занимают больше памяти, их дольше сравнивать и хешировать.
    
- **Решение:** Использовать целочисленные типы (`integer`, `bigint`) для первичных и внешних ключей.
    
- **Результат:** Ускорение `JOIN`-ов в **2-5 раз**.
    

## `CLUSTER` Для Физической Сортировки Данных

- **Проблема:** Даже при наличии индекса, если запрос возвращает много строк, СУБД приходится читать данные с разных страниц на диске, что увеличивает количество операций ввода-вывода (IOPS).
- **Решение:** Физически пересортировать строки в таблице на диске в соответствии с порядком в часто используемом индексе.

```SQL
    -- Объявляем индекс для кластеризации
    CLUSTER pull_requests USING pull_requests_repository_id;
```

- **Примечание:**
    
 > `CLUSTER` устанавливает эксклюзивную блокировку на таблицу. Для продакшена следует использовать расширение `pg_repack`, которое делает то же самое без блокировок. Команду нужно выполнять регулярно.
- **Результат:** Ускорение в **2-5 раз**, особенно для "холодных" запросов, читающих с диска.

## `pg_hint_plan` — Подсказки Планировщику

- **Проблема:** Иногда планировщик PostgreSQL упорно строит неэффективный план, и стандартными методами на него не повлиять.
- **Решение:** Использовать расширение `pg_hint_plan` для прямого указания, как выполнять запрос.
- **Примеры использования:**
    1. **Коррекция оценки строк (`Rows`):** Умножить или задать абсолютное значение для оценки количества строк.
```SQL
/*+
Rows(pr c *100) -- Умножить оценку на 100
Rows(pr c #100) -- Установить оценку в 100
*/
SELECT ...
```

    2. **Порядок `JOIN`-ов (`Leading`):** Принудительно задать порядок соединения таблиц, что критически важно для производительности.

```SQL
/*+
Leading(pr (*VALUES* c)) -- Сначала фильтруем pr, потом соединяем с результатом VALUES
*/
SELECT ...
```

    3. **Выбор индекса (`IndexScan`):** Можно заставить планировщик использовать конкретный индекс (использовать с осторожностью).
